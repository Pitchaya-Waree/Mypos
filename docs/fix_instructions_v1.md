### ข้อ 2 — ลบหมวดหมู่กระทบทุกร้าน (ทำก่อน)

**ปัญหา**: `deleteCategory` ถูกเรียกโดยไม่ส่ง `shopId` ทำให้ `getProducts(shopId: null)` วนผ่านสินค้าของทุกร้าน

**ต้องทำ**
- ส่ง `_currentShopId` ให้ `deleteCategory` ทั้งใน `PosProvider` และ `LocalRepositoryRegistry`
- เปลี่ยน `shopId` ของ `deleteCategory` เป็นพารามิเตอร์ที่จำเป็นต้องส่ง (ไม่ให้เป็น null ได้)
- ตรวจเมธอดอื่นใน `DatabaseService` และ repository ที่รับ `shopId` แบบ optional แล้วสแกนข้ามทุกร้านได้ (เช่น `getProducts(shopId: null)`) รายงานรายชื่อที่พบ และแก้ตัวที่ถูกเรียกจากโค้ดที่ทำงานในขอบเขตร้านเดียว

**เกณฑ์ผ่าน**
- Test: มีร้าน A และ B สินค้าในร้าน B ใช้ `categoryId` ค่าเดียวกับร้าน A ลบหมวดหมู่ในร้าน A แล้ว `categoryId` ของสินค้าร้าน B ต้องไม่เปลี่ยน
- สินค้าของร้าน A ที่อยู่ในหมวดนั้นถูกย้ายไป "ไม่มีหมวดหมู่" ตามเดิม

### ข้อ 1 — ราคาทุนรั่วให้ Manager ในหน้าแก้ไขสินค้า

**ปัญหา**: ช่องราคาทุนใน dialog แก้ไขสินค้าแสดงและบันทึกให้ทุกคนที่แก้สินค้าได้ โดยไม่ตรวจ `pos.canViewCost(product)`

**ต้องทำ**
- ซ่อนช่องราคาทุนเมื่อ `!pos.canViewCost(product)` และตอนบันทึกต้อง **คงค่าทุนเดิมไว้** ห้ามเขียนทับเป็น 0 หรือ null
- ตรวจว่า `canViewCost` ตรงกับตารางสิทธิ์ใน `plan_v1.7.md` หัวข้อ 3: Owner เห็นทุกชิ้น ส่วน Manager และ Member เห็นเฉพาะสินค้าของศิลปินที่ผูกกับตัวเอง
- ตรวจจุดอื่นที่อาจแสดงราคาทุนและรายงานผล: รายการสินค้า, export CSV/Excel, หน้า preview ตอน import CSV, รายงาน, dialog คัดลอกสินค้า, หน้า settlement ถ้าพบการรั่ว ให้แก้ด้วยเงื่อนไข `canViewCost` เดียวกัน

**เกณฑ์ผ่าน**
- Manager ที่ผูกกับศิลปิน X เปิดสินค้าของศิลปิน Y: ไม่เห็นช่องราคาทุน และบันทึกแล้วค่าทุนเดิมไม่เปลี่ยน
- Manager เปิดสินค้าของศิลปิน X: เห็นและแก้ราคาทุนได้
- Owner เห็นและแก้ราคาทุนได้ทุกชิ้น

**หมายเหตุ**: การซ่อนช่องใน UI ไม่ใช่การรักษาความปลอดภัย การป้องกันจริงคือการแยก `productCosts` เป็นเอกสารต่างหากตามแผนตอนย้ายไป Firestore ห้ามรายงานข้อนี้ว่า "ปิดช่องโหว่ด้านความปลอดภัยแล้ว"

**ต้องทำ**: สร้าง `order.id` (UUID) ก่อนสร้างรายการสินค้า แล้วกำหนด `orderId: order.id` ให้ทุก `OrderItem`

### ข้อ 7 — สร้างร้านแล้วไม่มี Owner ใน members

**ปัญหา**: `createShop` สร้างร้านแต่ไม่สร้าง `Member(role: owner)` และสิทธิ์ตกไปที่ค่าเริ่มต้นที่ไม่ปลอดภัย

**ต้องทำ**
- ใน `createShop` ให้สร้าง `Member` ที่ `role: owner` ให้ `ownerUserId` ในขั้นตอนเดียวกัน
- ตรวจว่ามีการสร้างศิลปินเริ่มต้น (default artist) ของเจ้าของร้านหรือไม่ ถ้าไม่มีให้สร้าง (ตาม `plan_v1.7.md` หัวข้อ 7)
- ตรวจค่าเริ่มต้นของบทบาทเมื่อไม่พบ member ของผู้ใช้ ต้องเป็น **ไม่มีสิทธิ์** (least privilege) ห้ามตกไปเป็น owner หรือ manager
- การเรียก `createShop` ซ้ำต้องไม่สร้าง member หรือศิลปินซ้ำ

**เกณฑ์ผ่าน**
- Test: หลัง `createShop` ร้านมี member 1 คนบทบาท owner และมีศิลปินเริ่มต้น 1 คน
- Test: ผู้ใช้ที่ไม่มี member ในร้าน มีสิทธิ์เป็น "ไม่มีสิทธิ์" และ `canViewCost` กับการแก้ไขทั้งหมดได้ false
- ร้านมี Owner พอดี 1 คนเสมอ

### ข้อ 6 — ปรับสต็อกมือแล้วถูกบีบเป็น 0 + สต็อกติดลบต้องขายได้

**ปัญหา**: ตัวจัดการปรับสต็อกมือใช้ `newStock > 0 ? newStock : 0` ซึ่งขัดกับการตัดสินใจที่ให้สต็อกติดลบได้

**ต้องทำ**
- เอา clamp ออก ให้เก็บค่าติดลบได้
- บันทึก `StockMovement` ชนิด `adjust` โดย `qtyChange = newStock - oldStock`
- แสดงสต็อกติดลบเป็นสีเตือนในหน้าคลังและบนการ์ดสินค้าในหน้าขาย
- **ตรวจตะกร้า**: README เดิมระบุ test "Stock Limit Prevention" ซึ่งขัดกับการตัดสินใจนี้ ถ้าโค้ดตะกร้าหรือ test บล็อกการขายเมื่อเกินสต็อก ให้เปลี่ยนเป็น **แจ้งเตือนแต่ให้ขายต่อได้** (เช่น "สต็อกเหลือ X ขายต่อได้ สต็อกจะติดลบ") และแก้ test ให้ตรงกัน แล้วรายงานว่าแก้ที่ไหน

**เกณฑ์ผ่าน**
- Test: ปรับสต็อกเป็น -3 แล้วอ่านกลับได้ -3 และมี movement `adjust`
- Test: ขายสินค้าเกินสต็อกได้ มีการแจ้งเตือน และสต็อกหลังขายเป็นค่าติดลบที่ถูกต้อง

### ข้อ 9 — PosProvider ข้าม Repository layer (ช่วง B)

**ปัญหา**: `PosProvider` เรียก `DatabaseService` (Hive) ตรงๆ ไม่ผ่านสัญญาใน `lib/repositories/repositories.dart` ทำให้การย้ายไป Firestore ต้องเขียน provider ใหม่

**ต้องทำ**
- ให้ `PosProvider` รับ repository interface ผ่าน constructor แทนการใช้ `DatabaseService`
- เก็บตัวทำงานแบบ Hive ไว้ก่อน แต่ย้ายไปอยู่หลัง interface (เช่น `lib/repositories/local/`) ส่วนตัวทำงานแบบ Firestore จะเพิ่มทีหลังใน `lib/repositories/firestore/` **ในรอบนี้ห้ามถอด Hive**
- ชื่อเมธอดและกลุ่ม repository ให้สอดคล้องกับ `plan_v1.7.md` หัวข้อ 10.3 (AuthRepository, ShopRepository, MemberRepository, CatalogRepository, EventRepository, OrderRepository, StockRepository, SettlementRepository)
- **ข้อบังคับเรื่อง atomic**: การขาย 1 ครั้งต้องเป็นการเรียก repository เมธอดเดียว เช่น `OrderRepository.placeOrder(draft)` ที่ทำ 3 อย่างพร้อมกัน: บันทึกออเดอร์, ปรับสต็อกแบบ delta ต่อสินค้า, บันทึก `StockMovement` (ฝั่ง Hive ทำในบล็อกเดียวที่ไม่มี `await` คั่น ฝั่ง Firestore ภายหลังจะเป็น `WriteBatch`) `voidOrder` ทำแบบเดียวกัน `PosProvider` ห้ามประสานการเขียนหลายขั้นตอนเอง

**เกณฑ์ผ่าน**
- ค้นหาแล้วไม่พบ import `database_service.dart` ใน `pos_provider.dart` และใน `lib/views/`
- มี fake repository แบบ in-memory ให้ unit test `PosProvider` ได้โดยไม่แตะ Hive
- ทดสอบมือกับ Hive: ขาย, void, settlement ยังทำงานเหมือนเดิม

### ข้อ 3 — ตัดสต็อกจาก snapshot เก่าตอน checkout (ทำพร้อมข้อ 9)

**ปัญหา**: คำนวณ `cartItem.product.stock - cartItem.qty` จาก snapshot ในตะกร้า ถ้ามีการปรับสต็อกระหว่างที่สินค้าอยู่ในตะกร้า checkout จะเขียนทับ

**ต้องทำ**
- สร้างเมธอดปรับสต็อกแบบ **delta** ใน repository เช่น `adjustStock(productId, delta, {reason, orderId})` ที่อ่านค่าสดภายในเมธอดเอง ฝั่ง Firestore จะใช้ `FieldValue.increment` ตามแผนหัวข้อ 5.1
- checkout เรียกด้วย `delta = -qty` ต่อสินค้า ห้ามเขียนค่า stock แบบสัมบูรณ์ที่คำนวณจาก snapshot
- movement ของการขายใช้ id ที่กำหนดแน่นอน `sale_{orderId}_{productId}` เพื่อกันการสร้างซ้ำ

**เกณฑ์ผ่าน**
- Test: สินค้าสต็อก 10 อยู่ในตะกร้า (snapshot = 10) แล้วปรับสต็อกมือเป็น 20 จากนั้น checkout จำนวน 2 ผลลัพธ์ต้องเป็น 18 ไม่ใช่ 8
- Test: เรียก `placeOrder` ซ้ำด้วย `orderId` เดิม ต้องไม่ตัดสต็อกซ้ำ

### ข้อ 8 — ส่วนลดทั้งบิลเพี้ยนเมื่อแก้จำนวนในตะกร้า (ทำพร้อมข้อ 9)

**ปัญหา**: เปลี่ยนจำนวนหรือลบรายการ ไม่มีการคำนวณการแบ่งส่วนลดตามสัดส่วนใหม่ ทำให้ส่วนลดรวมหดโดยไม่รู้ตัว

**ต้องทำ**
- เก็บ "เจตนาส่วนลดทั้งบิล" ใน `PosProvider` เป็นชนิดและค่า (`percent` หรือ `amount`) แล้วคำนวณการแบ่งใหม่ทุกครั้งที่ตะกร้าเปลี่ยน (เพิ่ม ลบ เปลี่ยนจำนวน ล้างตะกร้า)
- แบบ `percent` คิดจากยอดรวมใหม่ แบบ `amount` คงยอดเดิมแต่ไม่เกินยอดรวมของตะกร้า
- ล้างเจตนาส่วนลดเมื่อตะกร้าว่างหรือหลัง checkout
- การปัดเศษ: แบ่งส่วนลดโดยให้ผลรวมของแต่ละศิลปินเท่ากับส่วนลดรวมทุกสตางค์ (ใช้จำนวนเต็มสตางค์ หรือวิธีเศษมากสุดได้ก่อน)
- ส่วนลดเฉพาะศิลปินยังแยกต่างหาก ไม่ถูกแบ่งใหม่ และคงลำดับการคิดตามที่โค้ดทำอยู่ ให้ระบุลำดับนั้นเป็น comment ในโค้ด

**เกณฑ์ผ่าน**
- Test: ศิลปิน A มูลค่า 300 และ B มูลค่า 700 ส่วนลดทั้งบิล 100 บาท → A ลด 30 และ B ลด 70
- Test: ลบรายการของ B ออก ส่วนลดต้องถูกคำนวณใหม่ตามกติกาข้างบน และไม่ทิ้งส่วนลดของ B ค้างในยอด
- Test: ผลรวมส่วนลดรายศิลปินเท่ากับส่วนลดรวมเสมอ รวมกรณีที่หารไม่ลงตัว (เช่น ส่วนลด 100 แบ่ง 3 ศิลปิน)

### ข้อ 11 — คำนวณ settlement ซ้ำสองที่ (ทำพร้อมข้อ 9)

**ต้องทำ**
- รวมการคำนวณไว้ที่ `SettlementRepository.computeForEvent` ที่เดียว แล้วให้ `PosProvider` เรียกผ่าน repository ลบโค้ดซ้ำใน `computeSettlementForEvent`
- กติกา: นับเฉพาะออเดอร์ `completed` ของงานนั้น ไม่นับ `voided`; ยอดรายศิลปินอ่านจาก `artistTotals` ของออเดอร์ (ต้องมี test ยืนยันว่า `artistTotals` เท่ากับผลรวมรายการสินค้า); `commissionAmount = gross × commissionRate / 100`; `netPayout = gross − commissionAmount`; ปัดเศษแบบเดียวกันทุกที่
- เฉพาะ Owner เห็นและตั้ง commission ได้ ตรวจว่า UI ซ่อนข้อมูลนี้จาก Manager และ Member

**เกณฑ์ผ่าน**
- Test: ยอดขายศิลปิน A รวม 1,000 บาท commission 10% → commission 100 และ net 900
- Test: ออเดอร์ที่ void แล้วไม่ถูกรวมใน gross
- ค้นหาแล้วเหลือโค้ดคำนวณ settlement เพียงที่เดียว

### ข้อ 4 — Firestore list rules ปฏิเสธ query ของ Member (ช่วง C)

**ปัญหา**: Rules ไม่ได้กรองผลลัพธ์ให้ ถ้า query ไม่มี `where('createdBy', '==', uid)` จะถูกปฏิเสธทั้ง query

**ต้องทำ**
- **ไม่ต้องแก้โครงสร้าง rules และไม่ต้องแยกออเดอร์เป็น subcollection** ให้แก้ฝั่ง client
- ให้ `OrderRepository.watchOrders` กำหนด query ตามบทบาท: Owner และ Manager ไม่ต้องกรอง `createdBy`; Member ต้องใส่ `where('createdBy', '==', uid)`
- ทำเช่นเดียวกับ `productCosts`: Manager และ Member ต้อง query ด้วย `where('artistId', '==', myArtistId)` ส่วน Owner ไม่ต้องกรอง
- เพิ่ม index ใน `firestore.indexes.json` ตามตารางในแผนหัวข้อ 9 (ออเดอร์: `createdBy`+`createdAtClient`, `createdBy`+`eventId`+`createdAtClient`, `eventId`+`createdAtClient`)
- ถ้ายังไม่มีตัวทำงานแบบ Firestore ให้ใส่คำอธิบายข้อกำหนดนี้ไว้ในเอกสารของ interface และเขียน rules test ไว้ก่อน

**เกณฑ์ผ่าน (Emulator)**
- Member list ออเดอร์โดยไม่กรอง `createdBy` → ถูกปฏิเสธ
- Member list โดยกรอง `createdBy == uid` ของตัวเอง → ผ่าน
- Member กรองด้วย uid ของคนอื่น → ถูกปฏิเสธ
- Owner และ Manager list ทั้งร้านโดยไม่กรอง → ผ่าน
- Member อ่าน `productCosts` ของศิลปินอื่น → ถูกปฏิเสธ

### ข้อ 5 — rules ล็อกการสร้างร้าน แต่ Spark ใช้ Cloud Functions ไม่ได้ (ช่วง C)

**ปัญหา**: `firestore.rules` ห้าม client เขียน `shops`, `members`, `memberships` เพราะออกแบบให้ `createShop` เป็น Cloud Function แต่ Functions ต้องใช้แผน Blaze ปัจจุบันโปรเจกต์ MyPOS ยังเป็น Spark

**ต้องทำ**
- **ห้ามแก้ `firestore.rules` ให้หลวม** ให้ไฟล์นี้คงเป็นเวอร์ชันเข้มตามแผน v1.7
- สร้างไฟล์แยก `firestore.rules.mvp` ที่ **ชั่วคราว** อนุญาต client สร้างร้านของตัวเองเท่านั้น ใส่ comment หัวไฟล์ว่า "TEMPORARY: ลบเมื่อ deploy Cloud Functions แล้ว" และห้าม deploy ไปที่ใดนอกจากโปรเจกต์ dev เมื่อผู้ใช้สั่งเอง
- ขอบเขตของ `firestore.rules.mvp`: อนุญาตเพียงการสร้างใน batch เดียว (1) เอกสาร `shops/{id}` ที่ `ownerUid == auth.uid` และยังไม่มีอยู่ (2) `members/{auth.uid}` ที่ `role == 'owner'` โดยตรวจด้วย `getAfter` ว่าร้านนั้นมีเจ้าของคือผู้เรียก และร้านยังไม่มีอยู่ก่อนหน้า (3) `users/{auth.uid}/memberships/{shopId}` ที่สอดคล้องกัน ส่วน update และ delete ของ `members` และ `memberships` ต้องยังถูกห้ามทั้งหมด
- กฎ MVP อื่นนอกจากนี้ให้เหมือน `firestore.rules`
- ฟีเจอร์ที่ต้องใช้ Functions (เชิญทีม, เปลี่ยนบทบาท, นำสมาชิกออก, โอนความเป็นเจ้าของ) ให้ซ่อนด้วย feature flag เช่น `kCloudFunctionsEnabled = false` เมื่อใช้ตัวทำงานแบบ Firestore กับ rules MVP เพื่อไม่ให้ UI มีปุ่มที่กดแล้วล้มเหลว โหมด Hive ไม่ได้รับผลกระทบ
- โครงกฎด้านบนเป็นแนวทาง **ยังไม่ได้ทดสอบ** ต้องเขียน rules test และผ่านใน Emulator ก่อนถือว่าใช้ได้

**เกณฑ์ผ่าน (Emulator)**
- ผู้ใช้สร้างร้านที่ `ownerUid` เป็นตัวเอง พร้อม member owner และ membership ใน batch เดียว → ผ่าน
- สร้างร้านโดยตั้ง `ownerUid` เป็นคนอื่น → ถูกปฏิเสธ
- สร้าง member `owner` ในร้านที่มีอยู่แล้ว → ถูกปฏิเสธ
- สร้าง member สำหรับ uid คนอื่น → ถูกปฏิเสธ
- แก้ role หรือลบ member ด้วย client → ถูกปฏิเสธ
- ผู้ใช้ที่ไม่ล็อกอินเขียนอะไรไม่ได้
- ชุด test ของ `firestore.rules` เดิม (เข้ม) ยังผ่านทั้งหมด
